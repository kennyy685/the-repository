## Bottom line
1. **HMP already has more of the "pro team" scaffolding than most solo shops** (release checklist,
   changelog, a real design-system file, worktrees in use, subagents split by role). The gap isn't
   inventing these - it's finishing the wiring between them.
2. **The single biggest unfinished piece is turning `pages/hmp-app.html` from one hand-edited
   ~8,400-line file into real separate files.** Claude's own Artifact tool already supports
   publishing a page with supporting files (`files: {"ds.css": ..., "icons.js": ...}`) served
   alongside it with real `<link>`/`<script src>` tags - no custom build script is even needed,
   which is simpler than what this round was asked to scope. This is the fix for "one file every
   builder edits" and for `git diff` being unreadable.
3. **`docs/release-checklist.md` already requires a check that doesn't exist yet**:
   `node tests/pages/design_gate.js`. The fixture (`tests/pages/design_gate_fixture.json`) is there;
   the script isn't. Every release since commit `33771c8` has been checking a box that has nothing
   behind it.
4. **Anthropic's own docs say coding work parallelizes worse than research** ("most coding tasks
   involve fewer truly parallelizable tasks than research, and LLM agents are not yet great at
   coordinating and delegating to other agents in real time" [4]) - which argues for *more* worktree
   + file-ownership discipline, not fancier agent-to-agent coordination. Keep it simple: separate
   files/folders per helper, not helpers negotiating live.
5. **"Feature flags / staged rollout" doesn't translate literally** - HMP has one user (FilthE).
   The useful version of that idea at this scale is a cheap kill-switch (a small on/off in
   `localStorage`/a config flag) so a bad new feature can be turned off without a full republish,
   not a real percentage-rollout system.

## How FilthE can work with the crew faster (plain English)
1. **Say when two things can happen at once** ("build the map AND fix the button colors") - that's
   the signal Code uses to split work into separate worktrees instead of one thing after another.
2. **Ask to see it before you judge it**: "show me light and dark on my phone size" gets you actual
   screenshots against the approved mockup, not someone's guess that it "should look right."
3. **Check "What's new" first** when a new version lands, before poking around - that line is
   written for you specifically, in plain English, no need to read code or ask what changed.
4. **If something feels off, say "turn it off"** rather than "fix it right now" - small risky
   features get a kill-switch, so undoing a bad idea is a flip, not a rebuild.
5. **One thread per kind of work** still helps even with worktrees - keep app-look asks separate
   from engine/scoring asks so nothing gets mixed into the wrong file.

## Details

### Track 1: how small product teams ship (search-summary sourced this round - see Watch out)
Stripe, Vercel, Linear, Figma, Chromatic and dev.to were all blocked by this session's network
policy today (org-level egress denial, not a missing page - see `/root/.ccr/README.md`), so this
track relies on search-engine summaries of those companies' own pages, not a direct read. Treat the
specific numbers below as directional, not verified - consistent with rounds 27-40's notes on
blocked egress for non-allowlisted domains.
- **Vercel Flags**: staged rollouts step a new feature through fixed percentages (5% -> 10% -> 25%
  -> 50% -> 100%, watching error rates at each stage before continuing) rather than flipping
  everyone at once [5].
- **Chromatic (Storybook's visual-testing tool)**: renders every component in isolation, saves a
  baseline screenshot on first run, and on every push compares new screenshots to the baseline,
  flagging anything that visibly changed for a human to approve [9].
- **Figma**: reports design systems with mature component libraries correlate with a 34% faster
  task-completion speed for the teams using them [7] (Figma's own number, not independently
  verified here).
- **Linear**: keeps a public, dated changelog (linear.app/changelog) and is widely cited as also
  surfacing "what's new" inside the product itself [6].

### Track 2: running many AI agents without collisions (primary-sourced - official docs, fetched directly)
- **Worktrees are Anthropic's own documented answer to this exact problem.** `claude --worktree
  <name>` creates an isolated checkout on its own branch under `.claude/worktrees/<name>/`, so
  "one session can build a feature while a second fixes a bug" without their edits colliding [1].
  Claude itself can also enter/switch worktrees mid-session with the `EnterWorktree`/`ExitWorktree`
  tools. Non-interactive (`-p`) runs don't auto-clean their worktree on exit - worth knowing since
  Cowork's hourly automation may need an explicit `git worktree remove` step eventually.
- **Subagents split work, worktrees isolate files - they're meant to be combined**, per the docs'
  own framing: "subagents split work up inside one session, and worktrees isolate file edits" [1].
  HMP's setup (Builder/Designer/Engine Mechanic/QA Tester as subagents, one now also in a worktree)
  is already using both halves of the documented pattern; the missing piece is doing it on purpose
  and consistently rather than by accident.
- **Hooks can block a tool call outright**, not just warn about it after the fact. `PreToolUse` can
  return a blocking decision before a Bash command runs [3] - the mechanism for actually enforcing
  "never `git add -A`" instead of relying on every helper remembering the CLAUDE.md sentence.
- **Anthropic's own multi-agent research writeup is a useful caution, not just encouragement**: it
  found multi-agent setups burn ~15x the tokens of a single chat, work best for "breadth-first"
  tasks that split cleanly into independent pieces, and that coding tasks have fewer of those than
  research does, because "LLM agents are not yet great at coordinating and delegating to other
  agents in real time" [4]. Its other concrete lesson (give each subagent a distinct, bounded task
  with an explicit output format, or agents duplicate each other's work) is exactly why the
  `improvement-scout` topics need to be non-overlapping when the Research Lead hands them out.

## Watch out
- Track 1 is search-summary sourced only (see above) - re-verify Vercel/Figma's specific numbers
  directly if this repo's network policy opens those domains later; don't quote the 34%/percentage
  figures to FilthE as verified fact.
- Don't build real feature-flag infrastructure (item 8's "real" version) - HMP has one user; a
  `localStorage` toggle gets the same safety at zero cost.
- Don't over-build multi-agent coordination on the strength of the research-system post - it's

  helpers on separate files/worktrees; don't try to make them negotiate live.

  existing test-before-report habit in `builder.md`.
